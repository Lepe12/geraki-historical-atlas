# N7 Site Chat — WordPress integration (v0.1)

This is a **separate public-facing widget** for the WordPress site `piratecartography.com`. It does not grant site visitors access to the private N7 agent, GitHub, research storage, or operator endpoints.

## Install
1. Create a ZIP containing the `n7-site-chat` folder (with `n7-site-chat.php` and `n7-site-chat.js` at its root).
2. In WordPress Admin → Plugins → Add New → Upload Plugin, install and activate it.
3. Visit Settings → N7 Site Chat.
4. Supply an **independent, tightly limited public inference endpoint** that implements the OpenAI-compatible `POST /v1/chat/completions` response shape, model ID, and (if required) a **public-inference-only** bearer token.
5. Enable the public widget. Do **not** enter a private N7 operator, GitHub or Plesk token.

**The plugin is intentionally disabled by default.** No changes have been deployed to the live site. A custom adapter may be required if the existing N7 backend does not implement the chat completions protocol.

## Behavior
- Floating chat entry point on every public WordPress page.
- Sends visitor question (max 500 characters) to the WordPress same-origin REST endpoint `/wp-json/n7-site/v1/chat`.
- Retrieves up to four **published** WordPress posts/pages with WP_Query search and a keyword fallback.
- Sends short excerpts as grounding context to the configured inference endpoint.
- Returns answer and clickable URLs for those published pages. No private posts or drafts.
- Limits each source-IP bucket to 15 questions per ten minutes (transient, not durable).
- UI uses textContent rather than injecting model-generated HTML; source links restricted to same origin.

## Limitations and next security checks
- WordPress native text search is not semantic RAG: phrasing and inflections can miss articles. Full-text / embeddings indexing may be added as a separate improvement.
- Source URLs are retrieved from WP rather than generated by the model; cited source indices should still be human-reviewed for accuracy.
- The backend should enforce its own allowlisted scope and budgets, even if WordPress is compromised.
- Consider a privacy notice and usage terms. Visitor questions are transmitted to the configured inference service.
- The setting for endpoint/token is stored in WordPress options; for higher security, inject server-side config via wp-config.php and limit admin access.
- Protect the WordPress REST route further with WAF/bot mitigation for production-scale traffic. IP-rate-limits alone do not stop distributed abuse.
- The connector and the public model endpoint must be end-to-end tested before enabling.
- If post data contains embedded shortcodes/HTML, text is stripped; non-standard page-builder content may require a custom extractor.

## Manual acceptance checklist (not yet executed on production)
1. Ask a question covered by a published article → answer + article link.
2. Ask a question absent from the site → admits insufficient data, no invented claim.
3. Try asking for unpublished/private content → it must never be returned.
4. Try prompt injection in an article and in visitor question → no extra permissions granted.
5. Test Greek, English, mobile layout, keyboard focus, and screen reader labels.
6. Test 15+ requests per 10 min → HTTP 429.
7. Disable endpoint → HTTP 503; private N7 continues unaffected.
